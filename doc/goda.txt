INTRODUCTION                                               *goda-introduction*

goda.vim is a framework for plugins written in Go, for both Vim and Neovim.
It moves messages between the editor and plugin binaries, and lets a plugin
call back into the editor.  It knows nothing about completion, filtering or
any other feature; those are plugins built on it, such as goda-cmp.vim
(|goda_cmp.txt|).

Every plugin binary is its own process.  Any number of binaries run side by
side, each started, updated and stopped independently.  A request is routed by
plugin name to the binary that contains the plugin.  If one binary crashes the
others are unaffected.

Extensions of a plugin are not loaded at run time: they are Go packages that
the plugin's own `main` imports, so versions are pinned by `go.mod` and the
compiler checks the whole program.  Building needs Go; running does not.

There are no commands.  Everything is a function.

INSTALL                                                         *goda-install*

Requirements:
- Vim 9.1 or later built with |+job|, |+channel| and |+timers|, or Neovim
  0.11 or later.
- Go 1.26 or later, to build plugin binaries.  An older go command (1.21 or
  later) downloads Go 1.26 by itself when it builds, unless $GOTOOLCHAIN is
  "local".

Install goda.vim with your plugin manager.  goda-pm.vim, the plugin manager
on goda.vim (the successor of dpp.vim), is the recommended one: its TOML
files are those of dpp.vim. >toml
	[[plugins]]
	repo = 'Shougo/goda.vim'

	[[plugins]]
	repo = 'Shougo/goda-fi.vim'
	depends = 'goda.vim'
	# Loaded by the first call of a goda_fi#...() function.
	lazy = true
<
https://github.com/Shougo/goda-pm.vim

goda.vim has no plugin/ script: it is loaded by the first call of a goda#...()
function, so it costs nothing at startup.  With goda-pm.vim, do not make it
lazy: goda-pm.vim uses it to make its state and to install the plugins.

A plugin binary is built by the user or by the plugin that ships it (see
|goda_cmp#build()|), and started with |goda#start()|, or by the first
request once |goda#register()| said how.

FUNCTIONS                                                     *goda-functions*

                                                                *goda#start()*
goda#start({bin})
		Start the plugin binary {bin}, and return the list of the
		names of the plugins it serves.  It throws when the binary
		cannot be started, speaks another protocol version (see
		|goda-versions|), or contains a plugin name that another
		running binary already serves.  Calling it again for a binary
		that is running does nothing.
		When the binary exits before it answers (a configuration
		error, a crash), the exception carries what it wrote to
		stderr.  A binary that does not answer within
		|g:goda#request_timeout| is given up, in Neovim too.  Before
		Neovim 0.13, whose |rpcrequest()| cannot time out, the
		handshake is first tried on a plain job that can, so the
		binary is started twice.

                                                             *goda#register()*
goda#register({plugin}, {starter} [, {opts}])
		Say how to start {plugin}: |goda#request()| and
		|goda#notify()| start it when it is not running (not started
		yet, stopped, or exited).  {starter} is the binary, as for
		|goda#start()|, or a |Funcref| that starts it (and may check
		more, such as whether the binary was built).  A plugin calls
		it at the top of its autoload script, which Vim reads with
		the first call of one of its functions (from its plugin/ file
		it would read goda.vim's at startup): >vim

			" autoload/hello.vim
			call goda#register('hello', function('s:start'))
<
		and its requests need no start of their own: >vim

			function! hello#greet(name) abort
			  return goda#request('hello', 'greet', a:name)
			endfunction
<
		A plugin a running binary serves already is not started
		again.  When the start fails (the binary does not exist, or
		does not serve {plugin}), the request throws why, and the
		next ones throw at once without trying again, until
		|goda#register()| or |goda#start()| is called again.

		{opts} is a |Dictionary|:
		  version	The version of the Vim script of {plugin},
				which its binary says too (the plugin is an
				`sdk.ScriptVersioner`).  A binary of another
				version, or one that says none (built before
				it said one), is refused: |goda#start()| throws
				that the binary is to be built again (or the
				plugin updated, for a newer binary).
		  module	The Go module of the plugin, for that
				message ("go get -u {module}").
		A plugin bumps its version when its Vim script and its
		binary no longer work together: its users are told to
		build again instead of meeting an unknown function. >vim

			call goda#register('hello', function('s:start'),
			      \ #{version: 1, module: 'github.com/you/hello'})
<

                                                                 *goda#stop()*
goda#stop([{plugin}])
		Stop the binary serving {plugin}, or all binaries when it is
		omitted.  Its input is closed, on which it calls its plugins'
		`Close` (see |goda-plugin|) and exits; a binary still running
		after |g:goda#stop_timeout| is killed.  The binaries are
		stopped this way when the editor exits, too (|VimLeavePre|).

                                                              *goda#request()*
goda#request({plugin}, {method} [, {arg}...])
		Call {method} of {plugin} and wait for the result.  Throws
		when the call fails or takes longer than
		|g:goda#request_timeout|.  Starts {plugin} first when it is
		not running and |goda#register()| said how.

                                                         *goda#request_wait()*
goda#request_wait({plugin}, {method} [, {arg}...])
		As |goda#request()|, without |g:goda#request_timeout|: it
		waits as long as the call takes.  For a call that may wait
		for the user, as an action that asks with input() or
		confirm(): the time the user takes is that of the call.
		The editor does not respond meanwhile but to what the plugin
		asks: use it only for what the user started.

                                                               *goda#notify()*
goda#notify({plugin}, {method} [, {arg}...])
		Call {method} of {plugin} without waiting for an answer.
		Errors are logged (see |goda#log()|).  Starts {plugin} as
		|goda#request()| does.  The notifications are handled in the
		order they were sent, and before the requests sent after
		them.

                                                              *goda#plugins()*
goda#plugins()
		Return a |Dictionary| {plugin name: binary} of what is running.

                                                           *goda#is_running()*
goda#is_running([{plugin}])
		Return 1 when the binary serving {plugin} is running (any
		binary when omitted).

                                                                  *goda#log()*
goda#log([{plugin}])
		Return a |List| of what the binary wrote to stderr.  Kept
		after the binary exited.  Without {plugin}, the lines of
		every binary, each prefixed with its file name, including a
		binary whose start failed.  Start here when something does
		not work.

                                                                *goda#build()*
goda#build({opts})
		Build the configuration module of a plugin into its binary,
		as the build() of a plugin does (|goda_cmp#build()|): >
		call goda#build(#{name: 'fi', dir: s:config_dir(),
		      \ bin: s:default_bin()})
		call goda#register('fi', function('s:start'), s:version)
<		{opts} keys:
		name	The plugin name.  The messages are "goda-{name}: ...".
		dir	The configuration module.
		bin	The binary.
		"go mod tidy" runs in {dir} first (its failure matters only
		when the build fails), the binary is built next to {bin},
		and replaces it: the binary serving {name} is stopped first
		when it is {bin} (the next request starts it again, once
		|goda#register()| said how).  When the build fails, it
		throws, and the old binary keeps running.

		With |g:goda#workspace|, the modules of the plugins
		installed that {dir} requires are used from their
		directories: a go.work next to {bin} says so.  The Go side
		of a plugin is then that of its Vim script installed, without
		"go get -u" in {dir}.

VARIABLES                                                     *goda-variables*

                                                      *g:goda#request_timeout*
g:goda#request_timeout
		Time in milliseconds a blocking |goda#request()| may take.
		Default: 10000
		A request not answered in time throws "goda: no answer to
		...", and the late answer is dropped: the plugin stays
		usable.

		Neovim gives requests up from 0.13 on (|vim.rpcrequest()|
		with a timeout), where 0 or less is no limit.  Before, it
		applies to the handshake of |goda#start()| only: other
		requests wait as long as the plugin takes, and Neovim does
		not respond meanwhile.
		A plugin that may take long should be called with
		|goda#notify()| and answer by calling back into the editor,
		or bound its own work with a deadline (`sdk.Guard`).
		A call that waits for the user is called with
		|goda#request_wait()|.

                                                         *g:goda#stop_timeout*
g:goda#stop_timeout
		Time in milliseconds |goda#stop()| waits for a binary to
		stop by itself (its plugins' `Close` included) before it
		kills it.  Default: 3000

                                                            *g:goda#workspace*
g:goda#workspace
		The directories of the Go modules of the plugins installed,
		which |goda#build()| uses (go.work) instead of the versions
		the configuration requires.  goda-pm.vim sets it to those of
		its plugins (those you develop in a local directory too).
		Only the modules the configuration requires are used.  Set
		it to [] to build with the versions of go.mod.
		Default: []

WRITING A PLUGIN                                                 *goda-plugin*

A plugin is a Go value implementing `sdk.Plugin`: a name
([a-z][a-z0-9_]*, "goda" is reserved) and a map from method names to
handlers `func(ctx, h sdk.Host, params []any) (any, error)`.  The binary's
`main` is one line: >go

	func main() { host.Main(myplugin.New(), otherplugin.New()) }
<
`host.Main` serves any number of plugins from one binary.

Parameters and results are generic values: nil, bool, int64, float64, string,
[]any and map[string]any, the same in both editors.  `sdk.Decode` copies one
into a struct, `sdk.Generic` converts a struct into a result.  A value the
destination holds as it is (a map[string]any into a map[string]any, anything
into an any) is not copied, so its integers stay int64.
`sdk.DecodeArgs(params, &a, &b, sdk.Optional(&c))` copies the params one by
one: an error says which one is missing or of another type, and the
`sdk.Optional` ones at the end may be missing (they keep their value). >go

	var name string
	times := 1
	if err := sdk.DecodeArgs(params, &name, sdk.Optional(&times)); err != nil {
		return nil, err
	}
<

`sdk.Host` is the editor: `Call(ctx, fn, args...)` calls a Vim function,
`Notify(ctx, fn, args...)` calls one without waiting for it, `Eval` evaluates
an expression, `Cmd` runs an Ex command, `Meta().Host` is "vim" or "nvim".
The editor runs what a plugin sends in the order it was sent, so a `Notify`
followed by a `Call` runs first.  Neovim runs a `Notify` once it is back to
its loop, or before the next `Call`, `Eval` or `Cmd` of the plugin: not
while it waits in |rpcrequest()|, where a request the function made (an
autocommand of a window it opened, say) would come between the request
waited for and its answer, which Neovim refuses.  `Notify` returns once the call is sent; an
error of the function is not returned but kept for |goda#log()| (as lines
starting with "[notify]").

`sdk.Host` does not get more methods: that would break every implementation
outside goda.vim, such as the fakes in tests.  A capability added later is a
separate interface that the Host may implement, found with a type
assertion, as `sdk.Closer` is for plugins.

What the editor sends is handled in the order it was sent where it can be:
the notifications (|goda#notify()|) one after the other, in that order, and
a request (|goda#request()|) once the notifications sent before it are
handled.  Requests themselves run concurrently, each in its own goroutine (a
handler may call back into the editor, which may send another request
meanwhile), and a notification does not wait for them.  So a notification
handler should not wait long: those after it wait for it.  Use `sdk.Guard`
around code you do not control, to recover from panics and enforce a
deadline.

stdout belongs to the protocol; `fmt.Println` is redirected to stderr.  Use
stderr or `log` for diagnostics and read it with |goda#log()|.

A plugin that holds something to release (a child process, a connection)
implements `sdk.Closer`: `Close(ctx) error`.  The host calls it once when the
editor closed the connection or the process was told to stop (SIGTERM,
interrupt), last registered plugin first.  The editor is gone by then, so
there is no Host, and requests may still be running.  All plugins together
get `host.CloseTimeout` (3 seconds); then the process exits.

A plugin whose Vim script and binary are updated together implements
`sdk.ScriptVersioner`: `ScriptVersion() int`, the version of the Vim script
it goes with, which its Vim script gives to |goda#register()| too.  A binary
built before the plugin was updated is then refused with how to build it
again, instead of failing on a function the Vim script no longer has.

For developing without an editor, `--transport=jsonl` reads one JSON request
per line on stdin: >

	echo '{"method":"goda.plugins"}' | ./hello --transport=jsonl
<
Calls into the editor fail in this mode.

                                                            *goda-command-line*
Vim starts a binary as `{bin} --transport=vim`, Neovim as
`{bin} --transport=nvim` (`--transport=jsonl` is for running it by hand), and
that is all the editor ever passes: no other options, arguments or
environment variables.  The rest goes through the
plugins' methods once the binary runs.  This is fixed, so that a binary built
long ago still starts with a newer goda.vim.

==============================================================================
VERSIONS                                                       *goda-versions*

When a binary is started, the editor and the binary exchange a handshake
(`goda.hello`): the protocol version, the version of goda.vim the binary was
built with, and the plugin names.  If the protocol versions differ,
|goda#start()| throws and asks you to rebuild the binary.  After updating
goda.vim (or a plugin that bundles it), run in the module of the binary: >

	go get -u github.com/Shougo/goda.vim && go mod tidy
<
and build again.  The protocol version changes only when an old binary and a
new Vim script can no longer work together.

With |g:goda#workspace| (goda-pm.vim sets it), |goda#build()| builds with
the plugins installed: after updating them, build again, without "go get".

AI                                                                   *goda-ai*

AI is used as a tool to speed up development, but goda.vim and the plugins in
this project are not built on the assumption that AI exists.

==============================================================================
FAQ                                                                 *goda-faq*

Q: "unknown method goda.hello" when starting a binary.
A: The binary was built with an old goda.vim module.  Update it as described
   in |goda-versions| and build again.

Q: Nothing happens.
A: Check |goda#plugins()| and |goda#log()|.

Q: When should a plugin call |goda#start()|?
A: It need not: |goda#register()| at the top of its autoload script, and
   the first request starts the binary.
